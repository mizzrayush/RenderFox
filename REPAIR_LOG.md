## Ground rules for this pass

- **No 3D software is installed on this machine.** No Blender, Maya, Unreal or C4D anywhere (`C:\Program Files\Blender Foundation` absent, nothing on PATH). Real DCC rendering cannot be verified here — correctness comes from the mock DCC harness plus reading the diff. Never claim a real render works.
- Repo remote: `https://github.com/mizzrayush/RenderFox` (private). Baseline = commit `1727f94` "Baseline: RenderFox pre-repair snapshot", pushed to `origin/main`.
- Binaries, model weights, packaged builds and `patch_script/` are gitignored. GitHub rejects single files over 100 MB; the folder is 4.2 GB.
- One commit per fix area, so any single change is revertable.
- Surgical edits only. No loss: account for every deleted line before calling something removed.
- Backend owns the vocabulary. When UI and backend disagree on a parameter name, fix the **caller**, not by adding a compatibility alias in the backend.
- A bare `(:NNN)` inside a phase paragraph points at a line of the file that paragraph is about, **after** that phase's edits; every one in 6a-6f was re-resolved against the current files on 2026-11-05. A citation that describes the pre-repair code says `as it stood at HEAD` and keeps the old number, because that number is the evidence. When a paragraph grows a file, re-resolve before trusting a range.
- **What the app is, in the user's words:** *"i want a very powerful software for working complementary with a 3d rendering software"*. It is not a renderer - it is the desk the DCCs work on. Feature additions are now authorised in this pass (*"you can add as many features as you would like just ensure they are connected"*) under one condition: **a feature that is not connected to the shared backbone does not ship.**
- **Coherence is a requirement, not a polish pass.** *"it doesnt feel like many apps just tabbed together...it should have an ecosystem"*, and the bar named is Blender - *"not in terms of features, or uses but in terms of coherence, stability, etc"*. Its checkable form is the Phase 9 contract below; from here on every phase and every new feature is measured against those seven invariants.
- **No emoji. SVG icons only. Nothing that reads as a gimmick** (*"no emojis, only svg icons, proper legit software not a gimmick"*). Every icon comes from `src/ui/icon_provider.py` (`SVG_ICONS`, rendered by `QSvgRenderer`) or `resources/icons/*.svg`; status marks in text are words ("Passed", "Failed"), never glyphs.
- **A control is never deleted to make a claim true - its backend gets written.** The UI may be reorganised freely (*"if you think the current ui is not good or it feels disconnected, you can reorganise the ui too as you like"*), but *"no feature is lost... in case you did it till now"*: when a button's wording promises work the code does not do, the fix is the missing backend, not the removed button. Every control removed earlier in this pass is listed as debt under Phase 9 and gets rebuilt; the only things that may be deleted are ones with no user-facing promise attached (whole fabricated panes whose every operation was also offered by the real one, and modules nothing imports).
- **The bar for feature scope:** *"maximum features so that a game developer, 3d modeller, or anyone using a 3d software just require one software along with his main 3d renderer... no need for other tool, like meshlab, lod generators, etc"*. RenderFox has to make MeshLab, standalone LOD tools, texture-bake utilities, format convertors and thumbnailers redundant - so each of those gets a real, measured path here, not an advertisement.
- **Every feature is script-testable, so every feature must be scripted.** This is pure Python - one process, no JS/C++/JUCE boundary (*"as this is a python app, so you can actually test every feature using scripts"*). No pane ships without a contract suite that clicks each control through Qt and reads the resulting file back; a control with no test is treated as unverified, the same as a defect.

## Ecosystem contract (Phase 9 - the coherence bar)

Measured on 2026-11-05, before any of this work: the app **already has** one icon system - `src/ui/icon_provider.py` defines `SVG_ICONS` (24×24 stroked paths with a `{color}` slot) and renders them through `QSvgRenderer` into a `QIcon` (`:410`), and 21 files import it - and it also still contains **88 emoji/pictograph characters spread over 16 files**: `✓`×24, `✗`×14, `✅`×12, `⚠`×8, then `📐 🤖 📂 🗑 🔧 💡 👁 🏷 ✏ ★ ⬇ ✨ ☆ 🚀 🔄 📅 🎵 🎯 ❌`, heaviest in `library_tab.py` (24), `ai_asset_tagger.py` (13), `model_tab.py` (12) and `ai_asset_tagger_ui.py` (11). `resources/icons/` holds 6 files, all chevron variants, referenced only from `src/ui/styles.py`. So this is **completion and enforcement**, not an invention: route the stragglers through the provider that exists and make a suite fail when anything bypasses it.

The seven invariants, each one testable, each one the reason Blender feels like one program:

1. **One selection.** The current model is application state owned in `src/core/`, not a `QListWidget`'s internal. Every pane that acts on a model reads it from there and says which model it means, so "Decimate" in Mesh Tools, "Thumbnail" in Batch and the Library's highlight are about the same file. Today each pane keeps its own notion of "selected" and the user reconciles them by hand.
2. **One vocabulary per operation.** An operation is implemented once - `src/processing/*` behind `ActionRegistry` - and every pane calls it. A private copy is the defect that killed the smart batch pane (6f: its own `_convert_format` that wrote nothing while the real `FormatConverter` sat in the repo), so `tests/test_ecosystem_contract.py` asserts the backend entry points appear only in the modules that own them.
3. **One verdict shape.** Every action reports in the same sentence form: what ran, which file it wrote, and the number **read back from that file**. No pane gets to invent a percentage, score or confidence figure (that habit produced the `confidence: 0.85` literals); anything not measured on disk is labelled a preview, and a preview is never counted as a result.
4. **One queue, one history.** Mesh operations, conversions and renders all run through `job_manager` with the progress/pause/stop semantics built in 4a-4c, and all append to the same history surface. A second runner with its own progress bar is how 6f's `ThreadPoolExecutor(max_workers=4)` came to exist beside the real batch engine.
5. **One way to be sent from.** Cross-pane jumps carry context both directions - `batch_prepare_for_file` (6f) is the pattern, not a special case - and every jump resolves its target by widget identity rather than an integer, which closes `main_window.py:244/:249/:254` and the hard-coded indices in `_open_in_model_viewer` / `_open_in_mesh_tools`.
6. **One theme, one icon set.** Icons come only from `icon_provider` / `resources/icons`; zero emoji or dingbat glyphs in any user-visible string; styling comes from the `styles.py` theme tokens, no per-pane colours, no gradients or glow.
7. **One config.** `config.json` is the only store; the backend reads what a pane writes, values are clamped where they are read, and no pane keeps a private copy of a setting the queue also consumes (`verify_software`, inventory `:117`, is the existing example of a setting that goes nowhere).

**Controls removed earlier in this pass are debt, and here is the full list.** Audited on 2026-11-05 by extracting every quoted control label deleted by any commit since the baseline (`1727f94..HEAD`, 49 labels) and grepping the current tree for each. Most of the misses are message strings from the fabricated code, not controls, and three of the six batch checkboxes only *changed wording* - baseline's `Process Subfolders` / `Overwrite Existing Files` / `Create Backup` are live as "Include subfolders" (`automation_tab.py:348`), "Replace a file already in the output folder" (`:350`) and "Copy each file into `_backup` first" (`:351`), and `Optimize Geometry` (baseline `:404`) is now the registered mesh actions themselves (`weld_vertices`, `repair_mesh`, `simplify_to_faces`, `simplify_by_ratio`). What genuinely disappeared, and what each one needs instead of a deletion:

1. **"Focus Selected"** - Rendering tab toolbar (`3ccd6ab`, baseline `rendering_tab.py:720-751`). Backend owed: a selection model on the viewport (`model_viewer.py`) - click-pick a face/object, then a frame that centres and fits it, reusing the same camera math `Reset View` already uses.
2. **"Samples: 128"** - the `QSpinBox(1..4096)` in the tab's quality row, deleted in `3ccd6ab`. Backend owed: the queue already knows how to ask an engine for quality settings (4a-4c), so samples go into `render_engines.py` as the engine's own flag (`--samples N` for Blender, the equivalents for the others) and the Rendering tab's Render button enqueues with it.
3. **"MP4 (H.264)"** - removed from `format_combo`, which is now `{'PNG Sequence', 'JPG Sequence'}` only (`rendering_tab.py:601`). The commit's own message said why it was wrong to keep: *the queue and VideoExporter render video, this tab never did* - so the backend is `VideoExporter`, already in the repo. Wire the combo to it and let the file be read back for its real container.
4. **"Preserve Materials"** - baseline `automation_tab.py:401`. Backend owed: a real per-format answer. Measure what assimp and pymeshlab keep across each pair already in the capability table (5a) - materials, UVs, vertex colours - then make the switch either change the call or refuse with the reason, and report what the written file actually still has.
5. **"Parallel Processing"** - baseline `automation_tab.py:372`. Backend owed: batch concurrency through the one `BatchProcessor` and the one job queue (invariant 4), with the same pause/stop semantics as 6d, not the `ThreadPoolExecutor(4)`-over-a-shared-mesh that the deleted smart batch pane used. 6d's note that "the mesh loaders are not reentrant, so two threads sharing one `MeshSets` is a crash and not a speedup" is still true of *that* path; the debt is a runner designed for concurrency, not the old checkbox re-enabled.
6. **"Target Format" / "LOD Levels" / "Reduction Factor"** - baseline `automation_tab.py:372-403`, deleted with the rest of 6d's dead group. Not lost, but degraded: the values are reachable today only as text typed into `batch_params_edit` (`automation_tab.py:343`, parsed at `:1851`), so a batch decimate works only if the user remembers the parameter's key name. Backend owed: a per-action parameter form generated from `parameter_names(action_id)` and the registry's own defaults, each field with a typable value box, so the control says what the action takes.

Feature work after that is cheap, which is the point: the connected additions this makes room for are a real **asset pipeline** view (one model, its LODs, its textures, its thumbnails, its conversions, one click each, all through the registry), DCC hand-off that writes the file the renderer expects and reports back, and per-asset history - each of them a pane that reads the shared selection and calls the shared backends, so none of them can become a second fake anything.

## Two-software bar (Phase 10 scope)

The user's own words set the target: *"its like one swiss knife software for everything you need except pure blender or 3d rendering, so that the main aim of users doing any kind of 3d just drops to just 2 software - 1 3d rendering like blender/c4d etc and one renderfox"*. So Phase 10 is not "add some features": it is **closing the workflow stages a 3D artist or game dev currently reaches for another program to do**, one stage at a time, each landing as backend + registry action + contract test + control, never as a control first.

### Phase 4a - render progress streamed while the renderer runs

The queue could not show progress because nothing read the renderer while it was alive: `get_progress()` returned a constant `0.0`, no caller invoked it, and all four `render_job` bodies were the same ~33 lines of `Popen` + `communicate()`, which by design hands you stdout only after the process has exited. One shared `execute()` in the base class replaces all four.

**`src/processing/render_engines.py` (+192 / -143)**

- Base class gained `_progress` state, `get_progress()` (real value now), `parse_progress()` (per-engine hook), `_percent()`, `_drain()`, `_observe()`, `_output_directory()`, `_files_in()`, `execute()`.
- `execute()` runs one reader thread per pipe. `_drain`'s comment records why: a renderer chatty on both streams fills one 4 KB buffer and blocks forever writing the other, which is exactly what `stdout.read()` then `stderr.read()` would do.
- Each engine keeps only its own frame-line grammar: Blender `Fra:7/9 Rendered …`, Maya `// Rendering frame 2 of 3 //`, Cinema 4D `Frame 2 rendered (2/3)`, Unreal `Frame 2 ( 2/3 )` **before** its `[ 100.0%]` bracket, because that bracket is the completion of the current frame, not of the job - taking the percent first makes a 3-frame job report 100% on frame 1.
- `render_job` in all four classes is now `return self.execute(self.get_render_command(job), job)`. The 143 deleted lines are those four duplicated bodies (~33 each), the constant `get_progress()` it replaces, the three imports none of them used (`time`, `dataclasses.dataclass`, `enum.Enum` - all already dead before this change), the function-local `import re` in `Cinema4DEngine.get_version`, and the raw `os.path.dirname(...)` expressions that `_output_directory`/`_mel_string` replaced. No behaviour was dropped: each body's `should_stop` check, return-code check and stderr capture are all in `execute()`, plus the two verdicts they did not have.
- Verdict rules, in order: user stopped → failed; non-zero exit → failed with the renderer's own stderr; **exit 0 with neither a frame line nor a new file** → failed ("exited cleanly without reporting a frame or writing anything to …"); exit 0 with new files but no recognised frame line → **success**, and progress closes at 100.
- That fourth rule is the safety net for the constraint this machine imposes: the parsers are written against syntax the mock records, and a real build of any of these packages could word its lines differently. Size + `st_mtime_ns` per file is evidence that does not depend on matching a string, so a differently-worded renderer costs a still bar, not a false failure. A re-render over the same filenames still shows up, because the mtimes move.
- `_output_directory` (`abspath(dirname(output_path))`) removes the `os.makedirs('')` crash the inventory noted at `render_engines.py:229` for a bare output filename, and hands every engine an **absolute** directory. A relative path is resolved against the *renderer's* cwd, which this app does not control, so Blender's `--render-output` is absolutized too and `test_15` renders a bare `blender_hero.png` through all four packages. *(Kept as the reason the directory is absolute; the method itself became `output_spec` in Phase 4c-1, which is also what fixed its `dirname` reading.)*

### Phase 4c-1 - one job's output means one thing

`job.output_path` meant two different things depending on who made the job, and every consumer picked a reading by guessing. `browse_output` in the dialog uses `getExistingDirectory`, so UI jobs and imported job JSON carry a **folder**; the scripting API carries a **file name** (`output_path="render.png"`). `dirname()` of a folder is the folder above it, and that single mismatch was three separate bugs: frames landing outside the chosen folder, Blender writing `D:\Renders0001.png`, and post-processing archiving/deleting the chosen folder's *parent*.

**`src/processing/render_engines.py`**

- `frame_stem(value)` (`:40`) and `output_spec(job) -> (absolute directory, frame-name stem)` (`:52`) are module-level functions, not `BaseRenderEngine` classmethods, because `postprocessor.py` has to answer the same question. A path that exists as a directory, or ends in a separator, is a directory and the stem is the job name; otherwise the stem is the file's own name without its extension, and the directory is `dirname` of it - made absolute by `os.path.abspath`, which is also what turns `''` ("right here") into the working directory instead of a crash.

### Phase 4c-2 - the queue runs the settings it is given

The queue had one job pointer, one engine pointer, and one worker thread: `_current_job` / `_render_engine` stood for "whatever is rendering", so every queue-side setting in the Settings tab was write-only and every per-job control acted on whichever job happened to be last. It is now a slot machine with a table of live renders.

**`src/core/job_manager.py`** (the bulk of the phase)

- `self._running: Dict[job_id, (job, engine)]` and `self._workers: Dict[job_id, Thread]`, both under `self._lock`. The two singletons are gone, and `current_job` with them (nothing left that may speak of one job). A signal is never emitted while holding `_lock` - it is a plain `threading.Lock`, and same-thread emissions run the slot before the lock is released.
- `_queue_policy()` (`:317`) reads `performance` from `config.json` on every pick: `max_concurrent` clamped to 1..16, `max_retries` to 0..100, `auto_retry`/`pause_on_error` coerced to bool, non-numbers falling back to `_DEFAULT_POLICY` (`:25`). Re-read rather than cached because a saved setting must not look broken until the next queue start; the file is a few hundred bytes and this runs once per render. The key names are the ones `settings_tab.py:1214-1221` writes - `test_26` pins that from both ends.
- `_next_pending()` (`:353`) sorts `(-_PRIORITY_RANK, insertion position)`. `Priority` is a string Enum with no order of its own, so the rank lives in a table (`:21`) that adding a level cannot silently reshuffle. It also skips any job still holding a slot: `_retry_pending` puts a job back to PENDING *before* its worker reaches the `finally` that frees the slot, and picking it in that gap hands one job two renderers and overwrites the slot it still holds.
- `_process_queue()` (`:369`) fills the free slots and hands each render to its own thread, wakes on `_queue_changed` instead of sleeping a second per pick, and stops picking when `_hold_after_failure` is set. When the queue stops itself it emits `processing_stopped` - the UI cannot see a stop nobody clicked.
- `_bind_progress(job)` (`:490`) returns a callback that writes into *that* job. The old one wrote into "the current job", so a two-slot queue let the short render's 100% close the long one. `_update_progress()` (`:576`) now polls every engine, clamped to 0..100, and treats an engine mid-teardown as no reading rather than a queue failure.
- `pause_job`/`resume_job`/`remove_job` work on the job id they were given. `_kill_renderer()` (`:219`) wakes a suspended process before terminating it (a SIGSTOPped renderer never sees the request on POSIX) and `remove_job` kills only that engine - dropping one render from a queue is not a request to cancel the others. A paused job deliberately keeps its slot: its process is alive and its frames are real.
- `get_queue_stats()` counts a snapshot; `estimate_remaining_time()` sums over every running job and averages in the completed ones instead of letting one job stand for the queue.

**The stop/launch race** - `stop_processing()` sets `_stop_event` and *then* snapshots the slots to kill them. A worker that had claimed a slot but not yet registered its engine was invisible to that snapshot, so it went on to launch a renderer nobody owned: the window closed with Blender still rendering. Closed at two points, because either side alone leaves a gap. `_run_job` reads `_stop_event` **inside** the lock that registers the engine (`:424-434`), so either the stop sees the engine and kills it or the worker sees the stop and never launches. And `execute()` no longer clears a pending stop before the launch (`render_engines.py:194-200`) - it reports the cancel instead, then consumes the flag so a later render on a reused engine is not cancelled by an old click - and re-checks right after `Popen` (`:216-221`), the only moment a process exists that no snapshot ever saw.

**`src/core/models.py`** - `retry_count: int = 0` on `RenderJob` (`:52`), so `max_retries` means the same for a hand-edited queue as for a hundred-job one.

**`tests/mock_dcc/mock_dcc.py`** - a scene may name a `launch_log`, and every renderer process appends one line before it does anything else. Counting launches is the only way to ask "how many renders did the queue actually start": a retried job rewrites the same frame names, so the output folder cannot answer it.

### Phase 4d-2 - a job asks for a format the renderer can be told about

`AddJobDialog` stored the extension the user picked (`png`, `jpg`, `exr`) and `BlenderEngine.get_render_command` upper-cased it onto the command line, so Blender was handed `--render-format JPG` and `EXR`. Those are not Blender format names: it reports `Unknown input format`, exits without rendering, and the job's only trace is a nonzero exit code several minutes later. Maya was worse because it fails quietly - `defaultRenderGlobals.imageFormat` takes a number, and the old lookup defaulted to `32` (png) for anything it did not know, so a `bmp` job wrote PNG files and the queue then looked for frames under an extension that never existed.

**`src/processing/render_engines.py`** - the vocabulary is now owned here: `_BLENDER_IMAGE_FORMATS` (`jpg -> JPEG`, `exr -> OPEN_EXR`, plus tiff/bmp/webp/tga/dpx/hdr) and `_MAYA_IMAGE_FORMATS` (the app's existing ids, unchanged), `image_format_choices(software_type)` for what a dialog may offer, and `image_format_value()` which translates or raises a `ValueError` naming the accepted options. `job.output_format` still stores the extension, because that is what a saved queue JSON carries and what the post-processor metadata reports; only the command line changes. Unreal and Cinema 4D translate nothing - the pipeline config carries the extension as written, and C4D's command line has no output-format switch at all, so the scene decides - and both keep `DEFAULT_IMAGE_FORMATS`. A refused format reaches `job.error_message` through `_run_job`, so the queue says *why* instead of "Render job failed".

**`src/ui/dashboard_tab.py`** - the format list is drawn from the engine, not from a literal: `update_format_choices()` (`:120`) repopulates on `currentIndexChanged` and keeps the user's choice when the new engine also accepts it, so Maya now offers four formats and never shows the `bmp` it cannot be told about. It falls back to `DEFAULT_IMAGE_FORMATS` while no engine is selected, so the field is never empty.
